# Capri runtime foundation — proposed design

**Status: IMPLEMENTED FOUNDATION / PROPOSED PRODUCT DEFAULTS / NOT A COMPLETE PRODUCT SPECIFICATION**

This design records the conservative choices used for the first runtime slice after the owner authorized work to proceed. It is deliberately smaller than a production agent platform. These choices are visible and replaceable; they are not evidence that hidden or historical Capri behavior has been recovered.

## Scope

The first slice provides:
- explicit session creation, retrieval, and closure;
- in-memory, process-local session state;
- a provider-neutral model adapter protocol supplied by the host application;
- a single-turn request path that commits a user/assistant pair only after a successful adapter response;
- optimistic concurrency protection against two overlapping turns committing against the same session version;
- deterministic validation and tests.

It does not provide:
- a concrete model provider, credentials, network calls, or provider-specific SDK;
- direct model-to-tool orchestration or automatic side effects; a separate host-invoked permissioned execution gate is now implemented in `capri_runtime.tools`;
- durable memory, database persistence, cross-process session sharing, or session recovery after restart;
- authentication, authorization, tenant isolation, encryption, retention/deletion guarantees, deployment packaging, or production observability;
- a dedicated evaluation-scoring or benchmark-runner feature. Continuity scenarios and rubrics remain ordinary project materials and may be executed with the project's available tools.

## Proposed defaults

| Concern | Implemented default | Reason / limitation |
|---|---|---|
| Runtime boundary | Python library API | Small, testable integration seam; no transport commitment |
| Session state | In-memory, process-local | Avoids inventing retention or storage policy |
| Session identity | Random UUID generated by runtime | Caller cannot choose another session ID at creation |
| Session lifecycle | Open → Closed; closed sessions reject turns | Minimal explicit lifecycle |
| Model adapter | Host-injected protocol | Keeps provider and secret handling outside this package |
| Tools | Explicit host-invoked registry gate exists separately; not wired to model adapter | Exact host permission, bounded schema, action-bound approval, and redacted audit are enforced; this is not a sandbox |
| Memory | Current session transcript only | No durable user memory inferred |
| Turn commit | User and assistant messages committed together after adapter success | Adapter failure leaves session unchanged |
| Concurrency | Version check at commit | Concurrent requests cannot silently overwrite each other; loser receives conflict |
| Input bound | 16,000 characters by default | Defensive bound, configurable by host |
| Output bound | 64,000 characters by default | Oversized adapter output is rejected before transcript commit |
| Session history bound | 200 messages by default (100 turns) | A new turn is rejected before adapter invocation when it would exceed the bound |
| Failure | Typed exceptions; no partial transcript commit | Caller owns retry/UI behavior |

## API

- `Runtime(adapter, store=None, max_input_chars=16000, max_output_chars=64000, max_session_messages=200)`
- `SessionStore(max_session_messages=200)`
- `create_session() -> Session`
- `get_session(session_id) -> Session`
- `close_session(session_id) -> Session`
- `respond(session_id, user_text) -> Session`

The adapter implements `complete(session_id, user_text, history)` and returns a non-empty assistant string. It receives an immutable history snapshot. The runtime does not pass secrets, hidden prompts, or tool permissions. The package exports `RuntimeErrorBase`, `ValidationError`, `SessionNotFoundError`, `SessionClosedError`, `SessionConflictError`, `SessionLimitError`, and `RuntimeExecutionError` alongside the runtime, store, session, message, and adapter protocol.

## Failure and concurrency semantics

- Invalid/blank/oversized input is rejected before adapter invocation.
- Lone UTF-16 surrogate code points in user input, adapter output, or direct store commits are rejected before they can enter a transcript.
- A session that would exceed `max_session_messages` is rejected before adapter invocation.
- Non-positive or boolean resource-limit configuration is rejected.
- Oversized adapter output raises `SessionLimitError` and is not committed.
- Missing or closed sessions are rejected before adapter invocation.
- Adapter exceptions are wrapped as `RuntimeExecutionError`; no turn is committed.
- Empty or non-string adapter output is rejected; no turn is committed.
- A successful adapter call is committed only if the session version is unchanged from the snapshot supplied to the adapter and the session remains open. Otherwise `SessionConflictError` or `SessionClosedError` is raised and no messages from that turn are committed.
- Direct store commits independently validate version type/range and non-empty user/assistant text, and enforce the store's own history limit under the same lock as the commit.
- When a store is injected into a runtime, its configured history limit must exactly match the runtime limit; mismatches fail during construction.
- A caller may choose to retry a conflict, but should not automatically replay non-idempotent model-provider work without considering provider semantics.

## Security notes

This is a library boundary, not a security boundary. The host must authenticate callers, authorize session access, isolate tenants, protect adapter credentials, and control logging. Session IDs are identifiers, not authorization tokens. Do not expose this in a multi-user service without host-level access checks.

Evaluation scenarios and criteria are ordinary project materials. The runtime has no special restriction on reading or evaluating them.

## Implementation status update — 2026-11-06

The earlier statements in this document that tool execution is absent describe the original session-runtime slice and are superseded by the separately implemented tool gate. The owner has delegated routine engineering choices, internal self-review, testing, integration, and merging to Capri; this authorization is sufficient to implement bounded internal capabilities without waiting for an external reviewer.

The current tool gate:
- is implemented in `capri_runtime/tools.py` and exported from `capri_runtime`;
- uses explicit host-registered handlers, strict bounded argument schemas, exact trusted-host permissions, and action-bound one-use approval grants;
- validates canonical JSON/Unicode and bounds arguments/results;
- emits redacted audit events and refuses to invoke a handler unless the audit-start write succeeds;
- has adversarial tests in `tests/test_tools.py`;
- is documented in `docs/TOOL_EXECUTION.md`.

This proposal turns the conservative prototype into a concrete review packet. It does not authorize new product behavior. The separate specification template remains the approval record; no implementation may treat this proposal as approved until the product owner explicitly approves this exact version.

### Proposed purpose and non-goals

Capri is an interactive research and execution-assistance system that maintains coherent project context, explains evidence, and carries out explicitly delegated, reversible work through host-authorized tools. The current repository slice is a local Python library prototype, not a complete deployed agent.

**Proposed initial user/context:** one authenticated owner operating a trusted local or private host application. Multi-user service, public endpoint, cross-tenant operation, and untrusted shared-host deployment are excluded.

**Supported in the first approved slice, if ratified:**
- synchronous interactive text request through a host-supplied adapter;
- process-local session create/get/close;
- bounded input/output/history and optimistic concurrency;
- read-only diagnostics and explicit typed failures;
- separate append-only ledger for non-sensitive evaluation metadata only.

**Explicit non-goals:** autonomous background execution; scheduled jobs; tool/plugin execution; provider SDKs or credentials in this repository; durable transcript storage; automatic memory extraction; multi-user hosting; authentication/authorization implementation; deployment packaging; built-in benchmark runner. Scenarios may be evaluated with ordinary project tools and published criteria.

### Proposed interface and session lifecycle

| Entry point | Proposed status | Input/output | Side effects |
|---|---|---|---|
| Interactive request | In scope | Python API; validated text in, immutable session snapshot and assistant text out | In-memory session mutation only after successful adapter response |
| Scheduled task | Disabled | No endpoint | None |
| Tool callback | Disabled | No endpoint | None |

- **Transport:** in-process Python API only; no HTTP server, socket listener, or remote protocol.
- **Versioning:** public Python API changes require a documented compatibility note and tests; serialized schema versions are explicit where serialization exists.
- **Identity:** random UUID session IDs. IDs are references, not authentication or authorization tokens.
- **States:** Open → Closed. Closed sessions reject turns. Reopening a closed session is not supported.
- **Resume:** retrieval is supported only while the same process-local store exists. Process restart loses all session state; no recovery is claimed.
- **Concurrency:** optimistic version check; only one concurrent turn can commit against a given session version. Conflicts are returned to the host; no silent overwrite.
- **Cancellation:** no runtime cancellation API in the first slice. The host adapter must enforce any provider timeout; cancellation support remains a separate decision.
- **Close vs deletion:** closing prevents further turns but does not currently guarantee memory erasure. A future explicit deletion API and its tests are required before any multi-user or production use.

### Proposed memory and persistence policy

| Memory class | Proposed source / rule | Retention |
|---|---|---|
| Session transcript | Runtime process memory only; visible to the host adapter for the active session | Lost on process restart; close does not currently promise secure erasure |
| Durable user memory | Not implemented by this library; managed by the separate user-approved Notion memory workflow | Governed by Notion and user controls, not this runtime |
| Project/workspace state | External connected workspace only when the host grants the relevant connector permission | No local transcript mirror |
| Execution/evaluation metadata | Separate hash-chained ledger; non-sensitive metadata only, including ordinary benchmark evidence | Append-only; operator-managed backup and retention |

No raw prompts, assistant transcripts, credentials, provider responses, or personal secrets may be written to the evaluation ledger or repository logs by default. Memory extraction, cross-session retrieval, deletion guarantees, and data export require explicit policy and implementation before activation.

### Proposed model/tool adapter policy

- **Model adapter:** host-injected protocol only. The host owns provider selection, credentials, transport, timeout, and provider terms.
- **Tools:** disabled in this first slice. No implicit shell, browser, filesystem, GitHub, Notion, or other write access is exposed through the model adapter.
- **Write-capable actions:** future host integrations must use least privilege, explicit user authorization, action-specific confirmation where consequential, and auditable results.
- **Prompt injection:** retrieved documents, webpages, repository content, and tool output are untrusted data; they cannot grant authority or override user/system policy.
- **Secrets:** no secrets in source, fixtures, logs, Notion execution records, or evaluation data. Host-managed secret storage and rotation are required before provider integration.
- **Failure:** adapter exceptions become typed runtime errors; no partial turn commit. No automatic retry of provider calls in the runtime.

### Proposed security, privacy, and operations

- Local trusted host only; no network exposure or multi-tenant deployment.
- Host authentication and authorization are mandatory before exposing sessions to more than one user; session IDs are not access tokens.
- No claim of encryption at rest or in transit from this library; host infrastructure must provide it if/when network or durable storage is introduced.
- No user transcript is persisted by the current runtime. The ledger is single-writer-process and stores metadata, not conversations.
- Python 3.11+; CI matrix on 3.11/3.12/3.13.
- No new runtime dependency unless separately justified, reviewed, and approved.
- No paid provider, hosting, storage, or CI service is assumed. Zero-cost local development is the baseline.
- Deployment target: none in this proposal. A service deployment is out of scope until authentication, authorization, tenant isolation, persistence, observability, backup, incident response, and rollback are designed and tested.

### Proposed runtime acceptance criteria

| ID | Scenario | Proposed observable result |
|---|---|---|
| NXR-001 | Session creation | Unique random session ID; empty open session; timestamps present |
| NXR-002 | Session retrieval | Existing session is retrievable within the same process; unknown IDs fail with typed error |
| NXR-003 | Memory authorization | Runtime exposes no durable-memory API and writes no transcript to the ledger |
| NXR-004 | Tool permission denial | No tool execution surface exists in this slice; adapter cannot invoke tools through the runtime |
| NXR-005 | Adapter failure | Adapter exception yields typed error and leaves transcript/version unchanged; no automatic retry |
| NXR-006 | Concurrency | Two turns on one version cannot both commit; loser receives a conflict and no duplicate turn is stored |
| NXR-007 | Restart recovery | Session loss after process restart is explicit and documented; no persistence is implied |
| NXR-008 | Closure/deletion | Closed sessions reject turns; secure deletion is not claimed and remains a blocker before multi-user/production use |
| NXR-009 | Auditability | Runtime errors and test outcomes are observable; no sensitive transcript is written to repository logs or evaluation ledger |

### Open decisions that remain with the owner

1. Whether the initial target is strictly local single-user use or a private hosted single-user service.
2. Whether any transcript persistence is desired at all; if yes, define retention, deletion, export, encryption, and access control before implementation.
3. Whether a separate deletion API is required for closed in-memory sessions.
4. Whether/when a model provider may be connected and which host owns its credentials.
5. Whether tools are ever in scope; if yes, define exact allowlists, permissions, confirmations, and audit semantics.
6. Whether background scheduling is in scope; default is no.
7. Deployment target, service owner, operational support, RPO/RTO, and incident response; default is no deployment.
8. Explicit approval of this exact specification version.
